# אפיון בסיס הנתונים (DB Schema) - אפליקציית Daily

מסמך זה מגדיר את ארכיטקטורת בסיס הנתונים (PostgreSQL) עבור מערכת **Daily**. הארכיטקטורה תוכננה לתמוך ביישומי AI מבוססי סריקת מסמכים, עיבוד שפה טבעית (NLP) והתראות פרואקטיביות, תוך שמירה על ביצועים גבוהים וקשרים לוגיים תקינים.

---

## 1. דיאגרמת קשרי ישויות (ERD - Entity Relationship Diagram)

הקשרים המרכזיים בבסיס הנתונים מבוססים על ישות ה-`User` (משתמש) כישות אב:
* **User (1) ─── (0..N) Document** (פוליסות, טפסים ומסמכים שהועלו)
* **User (1) ─── (0..N) Receipt** (קבלות שנסרקו)
* **Receipt (1) ─── (1..N) ReceiptItem** (פירוט המוצרים בכל קבלה)
* **User (1) ─── (0..N) Reminder** (תזכורות ותורים)

```
  ┌─────────────────────────────────────────────────────────┐
  │                          USERS                          │
  └────────────────────────────┬────────────────────────────┘
                               │
         ┌─────────────────────┼─────────────────────┐
         ▼                     ▼                     ▼
  ┌─────────────┐       ┌─────────────┐       ┌─────────────┐
  │  DOCUMENTS  │       │  RECEIPTS   │       │  REMINDERS  │
  └─────────────┘       └──────┬──────┘       └─────────────┘
                               │
                               ▼
                        ┌─────────────┐
                        │RECEIPT_ITEMS│
                        └─────────────┘
```

## 2. מבנה הטבלאות וסוגי הנתונים

### טבלת משתמשים (`users`)
טבלה זו שומרת את פרטי הפרופיל והגדרות המשתמש שנקבעו בשלב ה-Onboarding.

| שם השדה | סוג נתון | הגבלות / מפתחות | תיאור |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | PRIMARY KEY, DEFAULT gen_random_uuid() | מזהה ייחודי של המשתמש |
| `email` | `VARCHAR(255)` | UNIQUE, NOT NULL | כתובת האימייל של המשתמש |
| `first_name` | `VARCHAR(100)` | NOT NULL | שם פרטי |
| `created_at` | `TIMESTAMP` | DEFAULT NOW() | זמן יצירת החשבון |
| `onboarding_settings` | `JSONB` | NOT NULL | קטגוריות נבחרות (למשל: קניות, רכב, בריאות) |

---

### טבלת מסמכים וביטוחים (`documents`)
טבלה זו משמשת לשמירת מסמכים ארוכי טווח כמו פוליסות ביטוח רכב, דירה, או טפסים רפואיים, לאחר שעברו ניתוח על ידי ה-AI Engine.

| שם השדה | סוג נתון | הגבלות / מפתחות | תיאור |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | PRIMARY KEY | מזהה ייחודי של המסמך |
| `user_id` | `UUID` | FOREIGN KEY -> `users(id)`, ON DELETE CASCADE | קישור למשתמש |
| `doc_type` | `VARCHAR(50)` | NOT NULL | סוג המסמך (`insurance_car`, `medical`, etc.) |
| `provider_name` | `VARCHAR(100)` | | שם החברה המנפיקה (למשל: הפניקס, הראל) |
| `file_url` | `TEXT` | NOT NULL | קישור לקובץ המאובטח בענן (S3/Cloud Storage) |
| `extracted_data` | `JSONB` | | המידע המובנה שחולץ ע"י ה-AI (כיסויים, אותם תנאים) |
| `expiration_date` | `DATE` | | תאריך תפוגת הפוליסה / תוקף המסמך |
| `annual_cost` | `NUMERIC(10,2)` | | עלות שנתית (אם רלוונטי) |
| `created_at` | `TIMESTAMP` | DEFAULT NOW() | זמן העלאת המסמך |

---

### טבלת קבלות (`receipts`)
מייצגת קבלה בודדת שנסרקה מסופרמרקט, רשת פארם או חנות קמעונאית.

| שם השדה | סוג נתון | הגבלות / מפתחות | תיאור |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | PRIMARY KEY | מזהה ייחודי של הקבלה |
| `user_id` | `UUID` | FOREIGN KEY -> `users(id)`, ON DELETE CASCADE | קישור למשתמש |
| `store_name` | `VARCHAR(150)` | NOT NULL | שם הרשת/החנות (שופרסל, רמי לוי) |
| `total_amount` | `NUMERIC(10,2)` | NOT NULL | סכום כולל לתשלום |
| `receipt_date` | `TIMESTAMP` | NOT NULL | תאריך הרכישה המקורי מהקבלה |
| `raw_ai_output` | `JSONB` | | הפלט הגולמי של מודל ה-Vision לצורכי גיבוי |
| `created_at` | `TIMESTAMP` | DEFAULT NOW() | זמן סריקת הקבלה במערכת |

---

### טבלת פריטי קבלה (`receipt_items`)
טבלה זו חיונית עבור **מנגנון ניתוח התדירות והמלצות החיסכון**. כל קבלה מפורקת לשורות של מוצרים בודדים.

| שם השדה | סוג נתון | הגבלות / מפתחות | תיאור |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | PRIMARY KEY | מזהה ייחודי של השורה |
| `receipt_id` | `UUID` | FOREIGN KEY -> `receipts(id)`, ON DELETE CASCADE | קישור לקבלת האב |
| `item_name` | `VARCHAR(255)` | NOT NULL | שם המוצר (למשל: "חלב תנובה 3%") |
| `quantity` | `INT` | DEFAULT 1, NOT NULL | כמות שנרכשה |
| `price_per_unit` | `NUMERIC(10,2)` | NOT NULL | מחיר ליחידה |

---

### טבלת תזכורות ותורים (`reminders`)
מנהלת את כל התורים והמשימות הבירוקרטיות. כוללת שדות ייעודיים להנעה מהירה לפעולה (Actionable UX).

| שם השדה | סוג נתון | הגבלות / מפתחות | תיאור |
| :--- | :--- | :--- | :--- |
| `id` | `UUID` | PRIMARY KEY | מזהה ייחודי של התזכורת |
| `user_id` | `UUID` | FOREIGN KEY -> `users(id)`, ON DELETE CASCADE | קישור למשתמש |
| `title` | `VARCHAR(255)` | NOT NULL | כותרת התזכורת (למשל: "תור לחיסון שנתי וטרינר") |
| `description` | `TEXT` | | פירוט נוסף |
| `scheduled_time` | `TIMESTAMP` | NOT NULL | זמן ביצוע התזכורת/התור |
| `phone_number` | `VARCHAR(20)` | | מספר טלפון לחיוג מהיר מהאפליקציה |
| `website_url` | `TEXT` | | קישור ישיר לאתר החברה/מרפאה לקביעת תור |
| `status` | `VARCHAR(20)` | DEFAULT 'pending' | סטטוס המשימה (`pending`, `completed`, `dismissed`) |
| `is_proactive` | `BOOLEAN` | DEFAULT FALSE | האם המשימה נוצרה אוטומטית ע"י ה-AI (למשל זיהוי פקיעת ביטוח) |

---

## 3. כיצד נשמרת כל יישות במערכת (Data Lifecycle)

### א. ישות משתמש (`User`)
* **מתי נוצרת:** בסיום תהליך ה-Onboarding הראשוני.
* **אופן השמירה:** פרטי המשתמש נשמרים עם מזהה UUID. בחירות ה-Onboarding נשמרות בשדה `onboarding_settings` במבנה `JSONB` דינמי (למשל: `{"groceries": true, "car_insurance": true}`). זה מאפשר להוסיף בעתיד קטגוריות ניהול חדשות מבלי לשנות את מבנה הטבלה.

### ב. ישות מסמך וביטוח (`Document`)
* **מתי נוצרת:** כשהמשתמש מעלה קובץ פוליסה/טופס במסך הפרופיל, או כשהודעה קולית מובילה להעלאת קובץ.
* **אופן השמירה:** 1. הקובץ הפיזי (PDF/Image) מועלה לשרת אחסון קבצים מאובטח (כמו AWS S3), ומחזיר כתובת `file_url`.
  2. ה-AI Engine (כמו GPT-4o Vision) מנתח את המסמך ומחלץ נתונים מובנים.
  3. נשמרת שורה בטבלת `documents`: המידע המובנה הכללי נשמר בשדות ייעודיים (`expiration_date`, `annual_cost`) לצורך שליפה מהירה ומיון, וכל שאר תתי-הסעיפים והאותיות הקטנות נשמרים בשדה `extracted_data` כ-`JSONB`.

### ג. ישות קבלה ופריטים (`Receipt` & `ReceiptItem`)
* **מתי נוצרת:** בלחיצה על כפתור המצלמה וצילום קבלה בסופר.
* **אופן השמירה:**
  1. תמונת הקבלה נשלחת ל-AI שמחזיר אובייקט JSON מובנה המכיל את שם החנות, התאריך, סך הכל, ורשימת הפריטים.
  2. נפתחת טרנזקציה (Transaction) בבסיס הנתונים:
     * ראשית, נשמרת ישות האב בטבלת `receipts`.
     * שנית, רשימת הפריטים מפורקת ונשמרת בטבלת `receipt_items` עם ה-`receipt_id` המתאים.
  3. **לוגיקת תדירות (AI background job):** שרת ה-Backend מריץ קוד המנתח את פריטי הקבלה לאורך זמן כדי לחשב ממוצע ימים בין רכישות של מוצר מסוים (למשל, קניית חלב כל 7 ימים), ומעדכן את המלצות רשימת הקניות החכמה.

### ד. ישות תזכורת ותור (`Reminder`)
* **מתי נוצרת:** ב-2 תרחישים:
  1. **ידנית / קולית:** המשתמש אומר "תזכירי לי וטרינר מחר ב-10:30". ה-AI מפענח את תאריך היעד, מוציא מהאינטרנט או מאנשי הקשר את הטלפון/אתר של המרפאה במידת האפשר, ושומר את הישות.
  2. **פרואקטיבית (אוטומטית):** מערכת ה-Backend מזהה ששדה `expiration_date` בטבלת `documents` קרוב (פחות מ-30 יום). המערכת מייצרת אוטומטית שורה בטבלת `reminders` עם סימון `is_proactive = true` המקפיץ את ההתראה האדומה במסך הבית של המשתמש.
